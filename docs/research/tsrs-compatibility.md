# TSRS compatibility with Typepeek's TypeScript runtime

Researched 2026-11-04, using TSRS's own documentation and source. Repository head observed: `48cf809ef3fc59e799d02872b247477e6c7d1c25`. No installation, prototype, or runtime comparison was performed.

**A dependency-only replacement is not compatible. A deliberate migration looks feasible, but 100% preservation of Typepeek's behavior is unproven.** TSRS targets the TypeScript 7.1 beta native compiler and its new JavaScript SDK. Its conformance reference is the Go compiler at `3e9236361fa97a9e6c685f4833ac457ae2d8c50a`, not the legacy TypeScript 6 JavaScript compiler API. The compatibility document reports extensive matching compiler baselines, while acknowledging remaining gaps. [Compatibility](https://github.com/oxc-project/tsrs/blob/main/docs/COMPATIBILITY.md), [SDK provenance](https://github.com/oxc-project/tsrs/blob/main/npm/tsrs/UPSTREAM.json).

The dependency context confirmed in [package.json](../../package.json) is runtime `@typescript/typescript6` 6.0.2, development `typescript` 7.0.2, and `@effect/tsgo` 0.63.0. The runtime alias currently loads compiler 6.0.3. Development compiler versions do not make the runtime's legacy objects compatible with the new SDK.

## Confirmed Typepeek dependencies

- [Installed program](../../src/inspection/installed-program.ts) creates programs with a custom `CompilerHost`, intercepting source reads, module resolution, type-reference resolution, and filesystem operations. This enforces package boundaries and compiler work budgets.
- [Declaration projection](../../src/inspection/declaration-projection.ts) uses `typeToTypeNode`, AST factory updates, transforms, and a printer to produce the Public Interface. [Signature inspection](../../src/inspection/signature-inspection.ts) also uses `typeParameterToDeclaration`; an equivalent migration path needs verification.
- [Package Documentation](../../src/inspection/package-documentation.ts) consumes symbol documentation as display parts and walks attached JSDoc syntax.
- [Compiler work sessions](../../src/inspection/compiler-work-session.ts) require the internal `getConditions` helper. [Resolution Variants](../../src/inspection/resolution-variant.ts) require internal `Version` and `VersionRange` helpers for versioned `types@...` export conditions. A replacement must supply equivalent behavior. Moving the compiler version from 6 to 7 can legitimately select a different declaration branch even with a perfectly conformant compiler.
- [Process enforcement](../../src/inspection/analysis-process.ts) applies Node heap settings and cancellation to the analysis subprocess. A native API server introduces another process whose memory and termination must be addressed.

## Concrete migration gaps

The source links below pin the observed TSRS revision; documentation links follow `main`.

| --- | --- |
| Imports and exports | The package root exports version metadata. Compiler access lives under `tsrs/sync` or `tsrs/async`; ASTs, factories, filesystem support, and paths have separate exports. Aliasing the current runtime import to `tsrs` cannot work. [Package exports](https://github.com/oxc-project/tsrs/blob/48cf809ef3fc59e799d02872b247477e6c7d1c25/npm/tsrs/package.json#L36). |
| Custom compiler hosts | The SDK accepts filesystem callbacks when creating its client, plus request filesystems and custom module resolvers. This offers a path for virtual files and controlled resolution, but does not accept the legacy `CompilerHost` object or its `getSourceFile` hook. Port host policy to the new filesystem/resolver contracts. This differs from legacy printer construction, handlers, `EmitHint`, and source-file arguments. Exact declaration text and comment preservation need comparison. [Printer implementation](https://github.com/oxc-project/tsrs/blob/48cf809ef3fc59e799d02872b247477e6c7d1c25/npm/tsrs/src/api/sync/api.ts#L6465). |
| Checker querying | The SDK exposes a `Checker` with export, alias, type, property, signature, and type-to-node queries. These operate through snapshot/project handles and remote requests, so equivalent names do not establish object or performance compatibility. [Checker source](https://github.com/oxc-project/tsrs/blob/48cf809ef3fc59e799d02872b247477e6c7d1c25/npm/tsrs/src/api/sync/api.ts#L4118). |

Documentation comments return a **string**; consumers expecting legacy display-part arrays must adapt. AST JSDoc helpers also exist. Symbol documentation is not simply missing. ## Feasibility and limits

The Node API is real: synchronous MessagePack and asynchronous JSON-RPC clients communicate with `tsrs --api`. Parsing, resolution, checker queries, AST editing, printing, and symbol documentation provide plausible building blocks for Typepeek. However, the coverage matrix marks many checker methods, symbol documentation, and printing as **partial**. Its reported 968 passing upstream SDK tests and 170 successfully exercised protocol methods do not establish universal response parity. [Node API and coverage matrix](https://github.com/oxc-project/tsrs/blob/main/docs/NODE_API.md).

Inference for Typepeek: porting its analyzer is possible in principle, subject to auditing Typepeek's compiler API calls. A separate native process also means revisiting subprocess-tree termination, total memory limits, filesystem evidence accounting, and deadline enforcement under [ADR-0002](../adr/0002-keep-inspection-static.md), [ADR-0004](../adr/0004-bound-every-inspection.md), and [ADR-0006](../adr/0006-isolate-each-inspection-in-a-subprocess.md). Keep external-code execution disabled. This research proposes no ADR change.

TSRS's documented differences explicitly compare against its pinned Go revision, not TS5/6. Its optional fast preset can change diagnostics and exit status; inherited `TSRS_FAST=1` also affects API processes. These settings must be controlled before any parity claim. [Differences and API caveats](https://github.com/oxc-project/tsrs/blob/main/docs/DEFAULTS.md), [fast-mode compatibility](https://github.com/oxc-project/tsrs/blob/main/docs/COMPATIBILITY.md).

Not tested: Typepeek's actual host callbacks, complete checker-method coverage, module-resolution variants, generated declaration formatting, overloads/aliases/merged symbols, attached Package Documentation fidelity, cancellation, resource budgets, native packaging, or performance. No evidence here proves equivalence between TS6 and TS7 type semantics. Some documentation can lag source—for example, `DEFAULTS.md` says Windows named pipes are unported while `NODE_API.md` describes them—so platform claims require release-specific verification. The README currently links to `docs/NODE_API.md`; attempted `docs/API.md` and root `COMPATIBILITY.md` paths returned 404.
